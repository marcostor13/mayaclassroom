# Almacenamiento en Cloudflare R2

Cómo obtener las cinco credenciales que Maya Classroom necesita para guardar
imágenes, vídeos y ficheros en R2 en lugar de en el disco del servidor.

Se tarda unos diez minutos. Hace falta una cuenta de Cloudflare con R2
activado; R2 exige añadir una tarjeta aunque el plan gratuito cubra 10 GB de
almacenamiento y las salidas de datos no se cobren nunca.

| Variable | De dónde sale |
|---|---|
| `R2_ACCOUNT_ID` | Identificador de la cuenta, en el panel de R2 |
| `R2_BUCKET` | El nombre que le dé al bucket al crearlo |
| `R2_ACCESS_KEY_ID` | Token de API de R2 |
| `R2_SECRET_ACCESS_KEY` | El mismo token, **solo se muestra una vez** |
| `R2_PUBLIC_URL` | Dominio público del bucket |

---

## 1 · Crear el bucket → `R2_BUCKET`

1. Entre en <https://dash.cloudflare.com> y elija su cuenta.
2. En el menú lateral, **R2 Object Storage** → **Create bucket**.
3. Póngale un nombre. Se recomienda uno por entorno, porque un despliegue de
   pruebas que escriba en el bucket de producción es difícil de deshacer:

   ```
   maya-classroom-prod
   maya-classroom-dev
   ```

4. En **Location**, deje `Automatic` salvo que necesite fijar jurisdicción de
   los datos (por RGPD, por ejemplo, puede elegir la Unión Europea).
5. **Create bucket**.

El nombre que ha escrito es `R2_BUCKET`.

## 2 · El identificador de cuenta → `R2_ACCOUNT_ID`

Estando en la sección **R2**, mire la columna derecha: hay un bloque
**Account details** con **Account ID** y un botón para copiarlo. Son 32
caracteres hexadecimales.

```
R2_ACCOUNT_ID=8f2c1d4e9a7b3f60c5e8d1a4b7f2c9e3
```

> Con este dato la aplicación compone sola el extremo de conexión
> (`https://<cuenta>.r2.cloudflarestorage.com`), así que no hay que
> escribirlo aparte.

## 3 · El token de API → `R2_ACCESS_KEY_ID` y `R2_SECRET_ACCESS_KEY`

1. En **R2**, pulse **Manage R2 API Tokens** (arriba a la derecha) y después
   **Create API token**.
2. **Token name**: algo que identifique el uso, por ejemplo
   `maya-classroom-prod`.
3. **Permissions**: **Object Read & Write**.

   No elija *Admin Read & Write*: ese permiso puede crear y **borrar buckets
   enteros**, y la aplicación solo necesita leer y escribir objetos.

4. **Specify bucket(s)**: elija **Apply to specific buckets only** y marque el
   bucket del paso 1. Si el token se filtrase, el daño queda acotado a ese
   bucket.
5. **TTL**: `Forever` si no tiene un procedimiento de rotación; si lo tiene,
   ponga la caducidad que corresponda y apúntela en el calendario, porque el
   día que expire dejarán de subirse ficheros sin más aviso que un error 500.
6. **Create API Token**.

La pantalla siguiente muestra, entre otras cosas:

```
Access Key ID:      a1b2c3d4e5f6...        → R2_ACCESS_KEY_ID
Secret Access Key:  9z8y7x6w5v4u...        → R2_SECRET_ACCESS_KEY
```

> **Copie el secreto ahora.** Al salir de esa pantalla no se puede volver a
> consultar: si lo pierde, hay que crear otro token y sustituir el anterior.

Ignore el resto de valores que muestra la pantalla (el extremo y los ejemplos
de `aws-cli`): la aplicación los deduce del identificador de cuenta.

## 4 · La dirección pública → `R2_PUBLIC_URL`

Este es el paso que más se olvida, y **sin él las imágenes no se ven** aunque
la subida funcione: los logos y las portadas se enlazan directamente al bucket
para que los pueda pedir alguien sin sesión, así que el bucket necesita una
dirección pública.

Hay dos formas. La segunda es la buena para producción.

### Opción A · Subdominio `r2.dev` (rápida, para pruebas)

1. Abra el bucket → pestaña **Settings**.
2. En **Public Development URL**, pulse **Enable** y confirme.
3. Copie la dirección que aparece:

   ```
   R2_PUBLIC_URL=https://pub-3f7a9c2e5b184d6a9c1e7f2b8d4a6c3e.r2.dev
   ```

Cloudflare limita el ancho de banda de `r2.dev` y **no lo recomienda para
producción**. Sirve para comprobar que todo funciona.

### Opción B · Dominio propio (recomendada)

Requiere que el dominio esté en la misma cuenta de Cloudflare.

1. Abra el bucket → **Settings** → **Custom Domains** → **Connect Domain**.
2. Escriba el subdominio que quiera usar, por ejemplo `cdn.suempresa.com`.
3. Cloudflare crea el registro DNS solo y emite el certificado. Tarda un par
   de minutos en quedar activo.
4. La variable es ese dominio, con `https://` y **sin barra final**:

   ```
   R2_PUBLIC_URL=https://cdn.suempresa.com
   ```

Ventajas sobre `r2.dev`: sin límite de ancho de banda, caché en la red de
Cloudflare, y las direcciones de sus imágenes llevan su marca en lugar de una
cadena aleatoria.

## 5 · Poner las variables

En **local**, en `.env.deploy`:

```bash
STORAGE_DRIVER=r2
R2_ACCOUNT_ID=8f2c1d4e9a7b3f60c5e8d1a4b7f2c9e3
R2_BUCKET=maya-classroom-prod
R2_ACCESS_KEY_ID=a1b2c3d4e5f6...
R2_SECRET_ACCESS_KEY=9z8y7x6w5v4u...
R2_PUBLIC_URL=https://cdn.suempresa.com
```

En **producción** van como variables de la aplicación de la API en Coolify.
Las tres credenciales son secretos: no deben acabar en el repositorio
(`.env.deploy` está en `.gitignore` precisamente por eso).

Después de cambiarlas hay que **reconstruir la API**, porque se leen al
arrancar:

```bash
bun run deploy --api
```

## 6 · Comprobar que funciona

1. Entre en **Administración → Empresa** y suba un logotipo.
2. Debe verse la vista previa al instante.
3. Pulse con el botón derecho sobre la imagen → *Copiar dirección*. Tiene que
   empezar por su `R2_PUBLIC_URL`, no por `/api/v1/files/...`.
4. Abra esa dirección en una ventana privada, sin sesión iniciada. Si la
   imagen se ve, está todo bien.

### Si algo falla

| Síntoma | Causa casi segura |
|---|---|
| La imagen **se descarga** en lugar de verse | El fichero se subió antes de este cambio, sin tipo de contenido. Vuelva a subirlo. |
| Error 403 al abrir la dirección pública | El bucket no tiene dominio público (paso 4) o `R2_PUBLIC_URL` apunta a otro sitio. |
| Error 500 al subir | Credenciales mal copiadas, o el token no tiene *Object Read & Write* sobre ese bucket. |
| La dirección sale como `/api/v1/files/...` | `STORAGE_DRIVER` no es `r2`, o la API no se ha reiniciado tras cambiarlo. |
| Sube pero no aparece en el bucket | El token apunta a un bucket distinto del de `R2_BUCKET`. |

## Qué se guarda y cómo

Las claves se reparten por uso, año y mes, con un identificador irrepetible:

```
image/branding/2026/09/3f7a9c2e-5b18-4d6a-9c1e-7f2b8d4a6c3e.png
image/course/2026/09/...
user/draft/2026/09/...
```

Como el nombre nunca se repite, el contenido de una clave no cambia jamás y se
sirve con caché permanente. Por eso al «cambiar» un logotipo se sube uno nuevo
en vez de sobrescribir el anterior.

**No todo se sirve desde R2.** Las imágenes públicas —logos, portadas, la
página pública— se enlazan al bucket, porque las pide gente sin sesión. Los
materiales de curso y las entregas siguen saliendo por `/api/v1/files/:id/download`,
que es donde se comprueban los permisos: un enlace directo al bucket saltaría
esa comprobación.

## Nota sobre CORS

**No hace falta configurarlo.** Los ficheros los sube el navegador a la API, y
es la API quien habla con R2; el navegador nunca se dirige a R2 salvo para
mostrar imágenes con `<img>`, que no está sujeto a CORS.

Solo tendría que añadir reglas de CORS en el bucket si en el futuro sirviera
tipografías desde R2 o leyera ficheros con `fetch()` desde el cliente.
